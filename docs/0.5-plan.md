# harness 0.5：改造方案、未决问题和三个试验（10-18）

> 10-18 夜里按这份计划做的改造、定下的事和没做的事，见 `docs/0.5-decisions.md`；分支 `0.5-runtime`。

这份文档记下 10-16 到 10-18 讨论定下的事，让在另一台电脑上接手的人不用翻聊天记录就能开工。设计细节在 设计稿仓库（未公开）的几份设计稿里，文末列了路径。这里写的是结论、还没定的事，以及下一步怎么做。

## 一、目标

0.5 版用 harness 替换 hands，由 harness 负责「想」，hands 退成执行层，只管「看」和「动手」。先让 harness 能独立跑起来，再接进 DeskMind app。这一版同时落地新的设计：看得宽、动得窄，分清东西归谁，按后果给动作分类，先给计划，每一步都核对，最后由模型写出要输入的内容。

起因：修 deskmind#73（Safari 搜索）时，在 hands 里一处一处打补丁，补好一处又冒出新问题。负责人的要求是：**做能泛化的能力，不要为单个任务逐个去修；单个任务的完成度不是第一目标。**

## 二、已经定下的事（负责人确认过）

| 事项 | 结论 |

| 谁替换谁 | harness 替换 hands 的决策；hands 只负责执行：看整台电脑、动手、把关 |

| 打包 | Node 加 esbuild 打成单个文件，做法照搬 app 里的 Python（`app/runtime.sh`）。比较过 bun、Node SEA、deno，选这个是因为它和开发、测试时用的运行环境一样 |

| 技能格式 | 用 Agent Skills 标准（SKILL.md） |

## 三、设计要点

### 三条底线（不管用什么模型、什么运行时都一样）

1. **谎报完成为 0**：没核实过的不能说「做完了」，结论只有三种：做成了、无法确认、做不到。
2. **未经同意的改动为 0**：动用户的东西、往外发东西，执行层只认 app 签发的同意凭证。
3. **随时可以停**：锁屏、超时、问了没人回答、预算用完，都如实停下，并撤回这次写下的东西。

### 不变的骨架：一个循环

```
看（整台电脑的状态和归属）
 → 想（模型：每一轮只有两种输出）
     ① 调一个工具（看 / 动手 / 问用户 / 读教程）
        → 守：执行层按结构算出最低后果类别，模型只能往上调
              只读、创建、改任务自己的东西：直接做
              改用户的东西、往外发：要有绑定到这个动作的签名凭证，没有就弹卡片问
        → 动：执行层把关（锁屏、窗口过期、验签、超时、停止开关）
        → 每步核对（改了状态或拿不准时）：前后对比、局部放大、结构对比
        → 原地打转？（动作加观察的结构指纹）→ 反思
        → 回到「看」
     ② 结束并报告
        → 结束钩子：拿不到 hands 的核对结论就不能结束
        → 核对：先查结构，再由模型看最终状态；证据不确定就算没做成
        → 没做成又还有额度：带上「还缺什么」接着做
        → 结果卡：改了什么、归谁、答案、按哪份教程做的；可以撤回
        → 用户反馈：学成教程或修订教程
```

- **归属：** 任务开始时 hands 记一份清单，清单上的都算用户的；任务后来创建的都算任务的。
- **同意凭证：** hands 出一道挑战（随机数，加上动作、对象、类别的哈希），app 用钥匙串或 Secure Enclave 里的密钥签名，hands 验签。凭证只能用一次、有有效期，范围分三档：只限这一个动作；这次任务里的这个对象；以后都按这条规则。
- **停：** app 直接通知 hands，不依赖运行时转达。
- **要往界面里打的字：** 由模型写出来，不再用代码从用户的话里摘。hands 里的 `value_candidates` 有十几条正则，到时退役。

### 可调的拆法：两种配置

| | 前沿模型配置 | 本地小模型配置 |
|---|---|---|
| 怎么跑 | 一个模型跑完整个循环，自己读技能描述 | 拆成多个角色（选教程、理解、计划、绑定、意图、后果分类、核对），把握不够就升级 |
| 原型基础 | pi 的 `pi-agent-core`：守用 `beforeToolCall`，每步核对用 `afterToolCall`，不核对不让结束用 `finishTurn`，停用 `abort` | 我们自己的编排器；选择题走 pi-ai 的 `classify()` |
| 隐私 | 真实屏幕内容要用户同意才能发出去 | 数据不出本机 |

### 技能层

- **格式：** 每份教程一个文件夹：`SKILL.md`（name、description，正文用自然语言写，不写正则），另有 `examples/`（确认过的例子和反例）、`checks.md`。我们自己的元数据放在 frontmatter 的 `metadata.deskmind` 下。
- **检索：**
  - 用户一提交，就用钩子把候选放进上下文。
  - 前沿配置：在额度内把所有描述列给模型。
  - 本地配置：先按结构筛（应用、文件类型、网站），再由 Brain 做选择题。按语义排序等教程多了再做。
- **生命周期：**
  - 学：做成并经用户确认后，写成教程。
  - 收下：照教程重做确认过的例子，结果一致才收下。
  - 用：结果卡上写明「按你上次的做法」，并且可以撤回。
  - 改：用反例修订。
  - 停用：只有确实是教程本身的错才停。
- **必须量出收益：** Agent S 第三版去掉记忆后分数反而更高。教程在复用题上得有实际提升。

### 和 app 的协议（hands.sock 下一版）

- 持久事件带序号，先落盘再发出；app 重连时带上 `after_seq`。
- 拒绝也记成一条事件，挂在对应的动作下。
- 支持中途补充要求（steer）；被打断时标记「这一步可能只做了一半」。
- 新增事件：计划卡、提问卡、结果卡、`respond`（撤回）、同意卡。
- 最终结论以 hands 给出的为准。

## 四、现在 harness 代码里要改的地方（来自 10-17 的接入方案）

- 「问用户」和 `GuiApp.observe/act` 改成异步（`src/orchestrator/index.ts`）。
- 界面操作能写进计划。现在 `opts.gui` 打开时会直接跳过规划。
- 界面状态要能核对。现在的核对只认文件（`C_CHECKS`）。
- 能把答案告诉用户（需要一个 `reply.answer` 之类的出口）。
- 新增入口 `src/cli/app.ts`：`app-run`、`respond`，往 stdout 写 JSON 事件，从 stdin 读回答。
- `src/registry/mac.ts` 不能再在用户的电脑上现编 `mactools`，改成预先编好，用 `DESKMIND_MACTOOLS` 指过去。
- 卡片和步骤的文字跟着请求的语言走，现在只有中文。
- 选一个固定的 Node LTS 版本。pi 要求 22.19 以上。
- `claude_cli` 后端只在开发时用，不能跟着 app 发出去。
- 模型网关的传输层改用 `pi-ai`，我们这边只保留角色表、结果校验、隐私分类把关。
- 技能层：`src/skills/rules.ts` 里的正则规则改成自然语言加例子；`library.ts` 改成按 Agent Skills 文件夹读写；`trySkill()` 挪到理解要求之前；停用计数按归因来算。
- 「学技能」这一类的底线问题（10-17 排查结论，详见 考卷文档）：
  - 理解要求时先翻教材；
  - 教材改存用户原话加例子；
  - 相关的几步一起核对；
  - 失败时撤回，交还给计划重做；
  - 停用按归因来算。

## 五、还没想清楚的事（按影响大小排）

1. **0.5 默认跑哪种配置。** 这是最大的空白。本地配置需要一个能写结构化内容的本地模型来做理解和计划，Brain 只会做选择题，而本地指令模型还没量过。前沿配置要先定谁付钱，真实屏幕内容发出去也要用户同意。
2. **同意凭证的交互。** 界面操作的步骤事先列不全，那么用户点一次「同意计划」，签多少张凭证？只签「这次任务里的这个对象」那一档，还是每步都弹？每次签名要不要指纹？
3. **「往外发」靠结构判断不出来。** 点「发送」按钮算不算往外发，光看结构判断不了，只能靠模型加保守的兜底。
4. **在本地核对界面任务。** 要看截图判断，Brain 看不了图，Eyes 只会定位。本地缺一个能看图判断的模型。
5. **撤回。** 界面操作大多撤不回，要列出一张「哪类动作能不能撤回」的表，还要想好中途被打断时怎么处理。
6. **自己做还是复用。** 前沿配置是基于 pi 的核心自己搭，还是直接用 Codex 当运行时，还没有实测。`classify()` 能不能直接对接 Brain 也要验证：两边 criteria 的格式不一样，Brain 自己的脚本用的是字典格式，看起来能兼容。
7. **问用户时进程怎么等。** 是一直挂着，还是先退出、等用户回答后再从运行记录恢复？app 中途重启怎么办？
8. **评测还没搭。** 练习场里还没放「用户自己的窗口和标签页」，macOSWorld 能在 Mac 上跑的那部分也还没接上。

## 六、下一步：三个试验（大约一周）

### 试验一：前沿配置跑通一个练习场任务（回答第 6 条，并看清第 3、4 条的实际难度）

- 在 harness 里用 `pi-agent-core` 搭一个单循环原型，加上 `pi-ai`。
- hands 先做一个最小的 MCP 服务，只要 `begin`、`snapshot`、`observe`、`act`、`verify`、`stop`。可以先基于现有的 `drivers/peekaboo.py` 包一层，不用一开始就把执行层做完。
- 用练习场的邮件任务跑。
- 把守、每步核对、结束钩子挂进 pi 的钩子里。
- **验收：** 练习场邮件任务能跑通；谎报完成为 0；在锁屏状态下以环境错误结束；记下调用次数和耗时；记下「往外发」和「核对」实际遇到了哪些难点。
- 有余力的话，用同样的 hands MCP 和技能，让 Codex CLI 也跑一遍：核对挂 Stop hook，找技能挂 UserPromptSubmit，两边比一比。

### 试验二：本地模型能不能做「理解要求、做计划」（回答第 1 条的本地那一半）

- 用 `mlx_lm.server`（app 里已经带了 mlx-lm 0.31.3），下载一两个本地指令模型，走 `local_chat` 后端。
- 在评测集 v2 的检查集（105 题，七类）上，只把 goal、plan、bind 三个角色换成本地模型，其余角色不变。
- **验收：** 各类的正确率、两条底线、每题耗时，和 dev-claude 基线并排列出来。结果决定 harness 这条路能不能做到全本地。
- 顺带用 `classify()` 对接 Brain，在 choice 角色上和现在的 systemone 后端对比一下。

### 试验三：同意凭证的交互规格（回答第 2 条）

- 写一份规格：
  - 一次「同意计划」覆盖什么，以及怎么变成凭证；
  - 三档范围在卡片上怎么呈现；
  - 签名要不要指纹；
  - 凭证有效期多长；
  - 被拒绝和过期时，界面上怎么显示。
- 附上卡片的界面草图。
- 交给负责人决定。

## 七、等负责人定的事

1. 前沿模型谁来付钱：用户自己的 OpenRouter key、新做一个 Anthropic 后端，还是由 DeskMind 统一代理。
2. Node 用哪个 LTS：24（当前的活跃版本），还是 22（维护到 2027 年 4 月，至少 22.19）。
3. README 的说法：现在写的是「全部用本机小模型」。
4. 要不要先做上面三个试验。
