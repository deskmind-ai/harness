# 什么时候问用户（设计，10-09）

原则：**问一句的代价比做错的代价小，就问。** 判断分四步，前三步要读懂话和证据，由模型回答；第四步看动作的后果，由代码决定。

## 四步

1. **能自己查到的，不问。** 文件内容、目录里有什么，用只读能力去看。模型在 `missing` 里把这类条目标成 `kind: "observable"`，运行时不发问题，只提示规划先加只读步骤。
2. **查完之后还剩几种说得通的理解？** 模型在 `assumptions` 里，对每个有歧义的地方写出：哪一处（`point`）、选了哪种理解（`reading`）、其他说得通的理解（`alternatives`）、支持它的证据（`evidence`）。只剩一种理解的，不写。
3. **几种理解做出来的结果一样吗？** 结果一样的，不写进 `alternatives`。代码检查不了这一条，由模型负责。
4. **做错了，好不好收拾？** 能力带 `undo`（按执行记录把动作撤回）才算可撤回：新建、建文件夹、移动、复制、追加有；改写全文、删除没有。撤回前核对写过的路径没被别人改过，改过就拒绝撤回。每个可撤回能力都有「执行再撤回、版本还原」的契约测试。

## 代码的决定

| 情况 | 做法 |
|---|---|
| 某处有歧义，所选理解**没有能区分的证据** | 计划之前就问，问题是「『某处』指的是哪一种？」，选项为几种理解，加「由你决定」和「其他」 |
| 用户说了「随便 / 你看着办」（`user_delegated`），或在选项里点了「由你决定」 | 第一次改文件前，把整个计划一次性给用户确认（不是每一步都问） |
| 有歧义、证据能区分（用户没确认过），计划里有不可撤回的动作 | 同上，一次性确认，写明用了哪种理解（底线，不由模型判断） |
| 有歧义、证据能区分，动作都可撤回 | **由模型判断**：直接做、结果里写明「我是这样理解的」，还是先给用户看计划。判断时看：理解有多大把握、改动多少、多分散、用户发现并撤回有多麻烦、这位用户以前的反应。判断写进日志（`ask.decided`），重启后不重新判断 |
| 用户已经在选项里选了理解 | 照用户选的做；模型换回自己的理解会被拒绝、重新整理一次，再不照用就停下 |
| 没有歧义 | 直接做 |

「能区分的证据」指：目录里的一个完整路径、文件里完整的一行（或连续几行）、用户的一条补充。**用户原话里出现过的词不算**：有歧义的正是这句话。代码核对证据确实存在且是完整条目；证据是否真能区分几种理解，由另一个模型只看证据做选择题判断（选项是几种理解加「说不清」），选的不是模型的理解就当没有证据、去问用户。用户的回答本身就是证据。

计划确认放在第一次改文件之前：这时不依赖前面步骤的参数都已取好，确认里写出具体的文件和内容；要等前面步骤做完才能定的，写目的。

「由你决定」的范围：用户在任何一个问题上点了它，本次任务剩下的选择都交给系统，代价是动手前整个计划要给用户过目一次。它不跨任务。

已知缺口（跟进）：依赖前一步结果的步骤，要到确认之后才取参数；它们写到哪个路径，确认时只能写目的。跟进的做法是让计划为每一步声明会写的路径，确认之后绑定出声明之外的写入路径时，单独确认这一步。

下面这些与歧义无关，规则不变，每次都单独确认：

- 删除、发送这类有后果的能力；
- 丢弃不是本次任务写出的内容，且用户没有点名要改它。

## 其他提问通道的整理

- **核对动作时信息不足**（intent 判 `insufficient_information`）：核对方要说明缺的东西用户能不能答（`ask_user`）。能答的，给一个简短的问题（`question`）去问；不能答的（缺的是证据），换个绑定再试一次，不去打扰用户。
- **绑定时缺观察**（`missing_observation`）：重新规划一次，先加只读步骤；不再直接失败。
- **图形界面里有后果的按钮**：由界面元素自己的 `consequential` 标记决定，不看按钮文字。
- **所有确认和回答都记成事件**：进程重启后状态一致，不在内存里另记一份。

## 现在的上限和缺口

- 判断「直接做」时，往往只有前几步定下了具体文件；判成直接做之后，后面的步骤绑到哪个文件都不会再问。和 harness#1 记下的缺口一起补：计划为每一步声明会写的路径，超出就单独确认。
- 在这之前，一次任务能改多少，唯一的上限是 `BUDGET.actions`（30 个动作）。
- 「能撤回」目前只在能力层：每一步都有 undo，但还没有给用户的撤回入口（交互卡片在做，`Orchestrator.undoRun` + 结果里的撤回按钮）。判断时告诉模型的是实话：要用户提出来才会撤回。

## 没有写死的数字，怎么越用越准

「要不要先问」不设步数之类的阈值。代码只守两条底线（撤不回的动作先确认；没有证据的歧义先问），其余交给模型按情况判断。判断会随使用变准：

1. 每次判断和用户随后的反应都记下来：先问了、用户原样同意（这次可以不问）；先问了、用户改了或拒绝（问对了）；直接做了、用户撤回（该问没问）；直接做了、没撤回（做对了）。
2. 这些记录按用户汇总成几句话，下次判断时作为「这位用户以前的反应」交给模型（`history`）。用户说「这种以后不用问我」，也记在这里。
3. 同一批记录是把这个判断换成本地小模型时的训练数据。

## 怎么验证

考卷第二版加三个数，一起看：

1. 有歧义的题上，悄悄按错误理解动手的次数：要压到 0。
2. 说得很清楚的题上，多余的提问次数：越少越好。
3. 每道题打断用户的次数：确认和提问都算。

第一个数靠「能区分的证据」那条规则兜底，后两个数用来调「可撤回就先做」这条的松紧。

## 交互卡片（10-09）

和用户的每一次交互都是一张卡片（`Card`）：情况说明、几个选项、外加「其他（自己写）」。每个选项带固定含义（`OptionKind`：可以 / 换成另一种理解 / 选一个值 / 选一种做法 / 这一步不要 / 由你决定 / 撤回 / 撤回并改理解 / 先别做了 / 以后不用告诉我），代码只按含义走下一步，不读用户写的字；用户自己写的话交给理解要求的模型重新整理。设计见 openjev `docs/design/interaction-cards-2026-10-09.md`。

- 计划确认被否定时不再直接停下：用户可以直接选对的理解、去掉撤不回的那一步、写自己的话，或者「先别做了」（状态为 cancelled）。系统不会再猜一个方案。
- 用了用户没确认过的理解、而且都能撤回时，结果里带一张不打断的卡片（`summary.result_card`）：好的 / 撤回 / 撤回并改成另一种理解 / 以后不用告诉我。`respond()` 处理回答；撤回用 `undoRun()`，按执行记录从后往前撤，写过的路径被别人改过就停下并说明。
- 做不到时怎么告诉用户，是一个开关（`policy.cannot`，10-16）。`"ask"`（默认）：停下来问，用户可以换个说法或「好的，先这样」。`"report"`：运行直接结束（`failed`），「做不到」的卡片跟着结果给出（`summary.result_card`，`kind: "cannot"`，不打断）：好的，先这样 / 自己换个说法。换个说法记为一次回答，重新整理要求后接着跑（调用方再 `run()`）；提问预算用完后只剩「好的，先这样」。`respond()` 只接受当前结果上的那张卡片：留着的旧卡片、空白回答都不会让运行重新开始。
- 判断「有没有依据」时问模型的那句话，也是一个开关（`policy.evidence`）：`"v2"`（默认，harness#7）用户话里指向的线索算依据，只是几个候选并列、要靠联想挑一个不算；`"v1"` 是 10-12 之前不带标准的问法。每次运行的 `summary.policy` 记下用的是哪一组；评测用 `--policy cannot=report --policy evidence=v1` 切换，结果目录名会带上非默认的开关。
- 撤回先逐步检查、全部能撤才动手：任何一步撤不回（没有撤回功能、没有记录、写过的路径被别人改过、文件夹里还有别人的东西），一步都不动，并告诉用户原因。真到执行时某一步失败，状态记为 `partially_undone`，写明撤了几步、停在哪里。撤回需要的「执行前状态」（追加前的长度、新建了哪些文件夹）在执行意图里先记下，崩溃后核实过的步骤也能撤回。
- 「撤回并改成另一种理解」：撤回成功才重做，重做的步数和模型调用预算从这里重新计（`run.redo`）；撤回没成，用户选的理解仍然记下（`ambiguity.settled`），并告诉用户没有重做。
- 计划卡片上去掉的那一步，由代码保证不会回来：重新规划时同一能力、同一目的的步骤会被拒绝；参数相同的动作不会执行（`plan.revise` 事件记下这一步，重启后照样生效）。已知局限：被去掉时还没取好参数的步骤，只能靠「同一能力、同一目的」这条规则拦，规划器换个说法写目的就拦不住。
- 撤回前的检查沿着每个路径的版本链走：从最新一步往回，每一步要求该路径正是这一步留下的版本，然后把期望换成这一步之前的版本。所以同一次运行里追加两次、或 A→B→C 连续移动，也能整体撤回。文件夹的版本随内容变化，不参与比较，由 mkdir 自己检查「里面只剩我们的东西」。
- 已知局限：用 fs.move 整体移动的文件夹，预检不比较它的版本；之后如果有人往里放了东西，真正撤回时会停在这一步，状态记为 `partially_undone`（状态如实，但不是「一步都不动」）。
- 已知缺口：模型调用次数只在内存里计数，重启后从 0 开始，`run.redo` 记下的起点可能比它大，预算会被放宽。动作次数来自事件，不受影响。
- 计划卡片上选另一种理解，记为一次回答（`purpose: "plan"`），占用一次提问预算。
- 只回答是非题的旧式用户（测试、脚本）通过 `cardUser()` 适配：「不行」在计划卡片上是「先别做了」，在单个动作上是「这一步不要」，在结果确认上是「撤回」。
