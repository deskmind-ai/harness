## 定下的（待 review）

| # | 事项 | 决定 | 为什么 |
|---|---|---|---|
| D1 | 模型渠道 | 网关加通用 `openai` 后端：`<provider>\|<model>`，provider 表只有 URL 和 key 的环境变量名（`yy`、`openrouter`）。配置 `yy-luna`、`yy-sol`、`yy-mix` | 加一个服务只改一行；key 不进代码、不进日志 |
| D2 | YY 上的 sol | sol 经 YY 走的是 Responses API，拒绝非严格 JSON Schema。网关碰到「Invalid schema」自动退到 `json_object`，schema 仍在 system prompt 里，zod 照常校验 | 不改各角色的 schema（optional 字段、record 都不符合 strict） |
| D3 | 执行层放哪 | 先在 harness 里用 TS 做一层 `src/executor/`：接口、归属清单、后果下限、同意凭证、把关；后面挂两种驱动：模拟桌面（测试、练习场）和 hands（真机）。hands 侧只做「看」和「动」 | 底线逻辑一处实现、两处驱动共用；hands 的 Python 执行层按同一协议对接 |
| D4 | 同意凭证的密码学 | Ed25519：app 持私钥签名，执行层只拿公钥验签。挑战 = 随机数 + 哈希(动作, 对象, 类别)。凭证三档：`action`（一次性）、`object`（本次任务内这个对象，类别不超过签的那档）、`rule`（以后都按这条，持久化） | 和设计稿一致；运行时拿不到私钥，伪造不了、重放不了 |
| D5 | 「同意计划」签多少张 | 计划卡上每个「改用户的东西」的对象签一张 `object` 档；「往外发」不随计划签，每次动作单独确认（`action` 档，卡片上带实际内容） | 回答未决问题 2：界面步骤事先列不全，但对象列得全；往外发的内容只有到那一步才确定 |
| D6 | 「往外发」判断不出来 | 执行层的下限用结构证据（元素标 `sends`，来自应用档案 / 表单提交语义）；模型再分一次类，只能往上调。两边都没判成往外发而实际发出去了，算底线事故，进题库 | 回答未决问题 3：结构 + 模型 + 保守兜底 |
| D7 | 前沿配置的运行时 | 用 `pi-agent-core` 1.3.0 + `pi-ai` 1.3.0 做单循环；把关在 `beforeToolCall`，每步核对在 `afterToolCall`，不核对不让结束在 `finishTurn`。版本钉死 | 试验一的做法；pi 更新快，钉版本 |
| D8 | 0.5 默认配置 | 默认前沿配置（`yy-luna` 跑循环，`verify` 等判断角色可换 sol）。本地小模型配置保留现有编排器，等试验二的数据 | 回答未决问题 1 的一半：现在能跑通闭环的是前沿配置 |
