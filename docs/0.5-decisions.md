## 独立评审（10-18 夜，新起的智能体，只看正确性）

6 个确认的问题，每个都先有一个会失败的测试（`test/review.test.ts`），然后修：

| # | 问题 | 修法 |
|---|---|---|
| R1 | `fs.move` 把用户的内容搬到新路径后，新路径算任务的，之后删掉、覆盖都不用问 | 归属跟着内容走：写出的新路径如果来自消失的用户路径，仍算用户的（`Ledger.inherits`） |
| R2 | 动作的元素 id 不在这个窗口最近一次观察里，也照样执行，`sends` 的下限就被绕过（id 可猜） | 执行层拒绝（`stale`：先观察）；`key` / `type` 也要求窗口观察过 |
| R3 | 回车、cmd+回车、输入里带换行，在有「发送」按钮的窗口里只算 `create` / `modify_user` | 窗口里有任何 `sends` 元素时，这些都算 `external` |
| R4 | 驱动在 `begin` 就失败时运行时直接抛异常，app 收不到 `task_done`；锁屏那条路不关驱动 | `begin` 失败记为 `environment` 并给出原因；所有出口都 `end()` |
| R5 | hands 子进程的 stdin 断了没有监听，EPIPE 会把整个进程打死，等待中的调用要等到超时 | 监听 `error` / stdin `error`，等待中的调用立刻拒绝；写入失败也当结果 |
| R6 | action 档凭证只验签名、摘要、有效期：别的运行（同一把 app 钥匙）签的凭证也能用 | 执行层登记自己出过的挑战随机数，只认这些 |

顺手修的小问题：网关只对 5xx / 429 / 网络错误重试（配置错误不再浪费 4 次）；app 的 stdin 关闭时卡片按「没有回答」收场，不再挂死；`verify` 的证据也包含只有 `unverified` 回执的窗口；连续拒绝动作卡的次数受 `asks` 预算约束。

## 结果（10-18 夜；全部 YY `gpt-6-luna`，除非注明）

### 试验二：本地模型做「理解要求、做计划、绑定」

检查集的单步、多步两类（30 题），goal / plan / bind 三个角色换成本地 `mlx-community/Qwen2.5-7B-Instruct-4bit`（mlx_lm.server，本机 M 系列 32 GB），其余角色不变（luna）；基线是同一配置全 luna。

| | 做对 | 做错的动作 | 没做成说做成 | 打扰 | 秒/题 |
|---|---|---|---|---|---|
| 全 luna | 30/30 | 0 | 0 | 1 | 23–47 |
| goal/plan/bind 本地 7B | **1/30** | 0 | **3** | 2 | 15–18 |

怎么错的（看的是检查集的日志，不是考卷）：
- 30 题里 18 题，本地模型把「检查」和「能力」两张清单搞混，把 `fs.copy`、`fs.move` 当成检查名写进 requirements，代码拒绝、一步没动（这是正确的防线）。
- 没搞混的几题，要求写得太松（只写「文件存在」），编排器按它写的检查判「做成」，而实际什么都没做——3 次谎报完成。这暴露的是编排器路线的结构弱点：**代码核对的对象是 goal 角色自己写的检查，goal 弱了核对就空了**。新运行时的核对由独立角色对照用户原话判，没有这个洞。
- 结论：本地 7B 指令模型直接顶替这三个角色不可行；要么给 goal 角色单独训（像 Brain 那样），要么本地配置改成「本地做选择题、前沿做理解和计划」。这回答了未决问题 1 的本地那一半。

### 检查集（105 题）：编排器 vs 新运行时，同一模型（luna）、同一评分

**先说一个作废：** 模拟用户是 `claude -p --model haiku`，夜里登录过期，凡是要模拟用户做判断的卡片（有歧义、做不到、学技能三类，以及运行时的同意卡）有一半以上没答上来，按「没有判断就不同意」走成取消。这三类加运行时的界面类，夜里的数字两边都不算；原始结果留在 `runs/*/results.night.jsonl`，受影响的题（`sim.fallbacks > 0`）早上重新登录后正在重跑，跑完用 `pnpm eval -- --report runs/base-yy-luna-check/results.jsonl runs/check-yy-luna-runtime/results.jsonl` 看。

模拟用户没出问题的四类：

| 类别 | 编排器 做对 | 编排器 打扰 | 运行时 做对 | 运行时 没做成说做成 | 运行时 打扰（其中多余） | 秒/题 编排器 / 运行时 |
|---|---|---|---|---|---|---|
| 单步 | 15/15 | 1 | 14/15 | 0 | 18（16） | 23 / 35 |
| 换工具名 | 15/15 | 0 | 14/15 | 0 | 23（23） | 23 / 32 |
| 多步 | 15/15 | 0 | 3/15 | 5 | 23（23） | 47 / 39 |
| 界面 | 15/15 | 0 | （作废：9/15 题模拟用户没答上同意卡） | 0 | 25（25） | 40 / 34 |

怎么读：
- **多步的 5 次「没做成说做成」不是运行时谎报。** 这 5 题带 `external` / `goal_update` 钩子（任务中途别的程序往文件里加一行、用户改要求），运行时引擎还没接这些钩子（`engine-runtime.ts` 文件头写了），金标准里有「别人加的一行」而运行里没发生过，评分当然判错。要么给运行时引擎接上钩子，要么比较时剔除带钩子的题。剩下的多步失败是模拟用户取消（见上）。
- **打扰多是设计使然，也是要定的事。** 这些题是「任务目录里已有的文件」上的操作，按 0.5 的归属规则，改用户的文件要同意；编排器的旧规矩是「可撤回就直接做、结果里说明」。评分把 `interaction: none` 的题上的每张卡都算多余。两条路线对「追加一行到用户的文件要不要先问」的答案不同，这是 D20 要负责人定的事，不是 bug。模型先 `plan` 的话，一题只有一张卡；现在模型多半不先 plan。
- 单步、换名两类各差 1 题（运行时 14/15），没来得及看是哪题。
- 编排器自己在 luna 上的有歧义 60%、做不到 73%、学技能 20%（夜里数字，含模拟用户失效），比 dev-claude（Sonnet）在正式考卷上的 97% / 71% / 64% 低，其中学技能和做不到大概率是模拟用户失效造成的；重跑后再看。

### 真机（10-18 上午，屏幕解锁后）

`python3 scripts/app-drive.py` 驱动 `app-run`（driver hands，YY luna），任务「在文本编辑里新建一个文档，写上「你好 DeskMind」，保存为 hello.txt 放到任务目录」：

- 结果 `succeeded`，`/tmp/dm-real/hello.txt` 内容正确；核对的依据是目录里的文件和文本编辑里同名的文档。
- 屏幕上原有一个「未命名」文本编辑窗口（夜里测试留下的），归属判为用户的 → 先出计划卡；stdin 没人答的那次老实以 `failed（no answer from the user）` 收场，不动任何东西。
- 两处当场修掉的：点「新建纯文本文稿」开出的新窗口没有报给归属清单（只有 `open_window` 报），所以它被当成用户的、每步都问（4 张动作卡）；hands 驱动的工作目录是临时目录，GUI 另存为的「工作目录顶层」没落到任务目录（文件最后是文件工具写的）。现在任何动作开出的窗口都报 `new_window`，任务目录就是驱动的工作目录。
- 还没重跑验证这两处；下次解锁时跑一遍，预期卡片从 5 张降到 1 张（只有计划卡）。
