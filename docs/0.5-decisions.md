|---|---|---|

| R4 | 驱动在 `begin` 就失败时运行时直接抛异常，app 收不到 `task_done`；锁屏那条路不关驱动 | `begin` 失败记为 `environment` 并给出原因；所有出口都 `end()` |
| R5 | hands 子进程的 stdin 断了没有监听，EPIPE 会把整个进程打死，等待中的调用要等到超时 | 监听 `error` / stdin `error`，等待中的调用立刻拒绝；写入失败也当结果 |
| R6 | action 档凭证只验签名、摘要、有效期：别的运行（同一把 app 钥匙）签的凭证也能用 | 执行层登记自己出过的挑战随机数，只认这些 |

### 试验二：本地模型做「理解要求、做计划、绑定」

检查集的单步、多步两类（30 题），goal / plan / bind 三个角色换成本地 `mlx-community/Qwen2.5-7B-Instruct-4bit`（mlx_lm.server，本机 M 系列 32 GB），其余角色不变（luna）；基线是同一配置全 luna。

| | 做对 | 做错的动作 | 没做成说做成 | 打扰 | 秒/题 |
|---|---|---|---|---|---|
| 全 luna | 30/30 | 0 | 0 | 1 | 23–47 |
| goal/plan/bind 本地 7B | **1/30** | 0 | **3** | 2 | 15–18 |

怎么错的（看的是检查集的日志，不是考卷）：
- 30 题里 18 题，本地模型把「检查」和「能力」两张清单搞混，把 `fs.copy`、`fs.move` 当成检查名写进 requirements，代码拒绝、一步没动（这是正确的防线）。
- 没搞混的几题，要求写得太松（只写「文件存在」），编排器按它写的检查判「做成」，而实际什么都没做——3 次谎报完成。这暴露的是编排器路线的结构弱点：**代码核对的对象是 goal 角色自己写的检查，goal 弱了核对就空了**。新运行时的核对由独立角色对照用户原话判，没有这个洞。
- 结论：本地 7B 指令模型直接顶替这三个角色不可行；要么给 goal 角色单独训（像 Brain 那样），要么本地配置改成「本地做选择题、前沿做理解和计划」。这回答了未决问题 1 的本地那一半。

怎么读（看的是检查集的日志，不是考卷）：

- **运行时的 5 次「谎报」里 3 次是评分口径，2 次是真问题。** 做不到类的 3 次是带 `crash` 钩子的题（金标准要的是「崩溃后停下」），运行时引擎没接崩溃恢复，文件其实做对了。多步类的 2 次是真的：任务中途别的程序往目标文件里加了一行，模型把它当成污染「更正」掉了——**别人的改动不是你的**，这条已经写进基础技能；编排器那边有 `externalChanges` 这个事实喂给核对角色，所以没犯。
- **运行时的 5 次「做错」：** 学技能 3 次是「整理一下这些会议纪要」这种没教过的模糊要求，模型自己发明了文件夹结构动手（计划卡上模拟用户用自己的话回答后它就做了）；编排器的歧义机制会先问。做不到 2 次是冲突题（目标文件已存在），模拟用户说「换个名字别覆盖」，模型照做了，而金标准要的是停下——这是评分口径和「照用户当场说的做」的分歧，要负责人定。
- **打扰：** 运行时在单步、换名、多步、界面四类上每题 1 张卡，全被评分记成多余——都是「改任务目录里已有的文件要先同意」（归属规则，D20）。编排器的旧规矩是可撤回就直接做。这不是 bug，是两条路线的取舍；模型先 `plan` 的话一题只有一张卡。
- **编排器自己在 luna 上**：有歧义 67%、做不到 87%、学技能 40%，比 Sonnet 在正式考卷上（97% / 71% / 64%）低；模型差了一档。
- **速度**：运行时在多步、有歧义、做不到、学技能上快 1.5–2.6 倍（一个循环代替七个角色）；单步、界面慢一些（多了观察和同意卡）。
- 结论：运行时这条路三条底线的机制是成立的（没有一次未经同意的改动、谎报的 2 次有明确的通用修法），但在模糊要求、冲突处理上还没有编排器积累的那套歧义机制；下一步是把「证据不足先问」的判断搬进运行时的基础技能和 `finish` 前的检查，而不是写规则。

### 崩溃恢复：中断期间别人改的文件没被记成「别人的改动」（10-18，复查 v2 的 3 次「谎报」时发现）

现象：做不到类的 cannot-003/007/011（崩溃钩子 + 崩溃后别的程序把目标文件整个改掉）。重跑带崩溃的进程后 `crashed: true`，但恢复后的执行层把崩溃后的文件状态当成了起点——日志里只有「intent / receipt」，没有任务开始时各文件的版本，所以比不出谁改过；核对证据里没有「被别的程序改过的文件」，模型和用户也都不知道。

改法（泛化，不针对题）：
- 日志开头多一条 `begin`（文件夹各路径的版本）；每条文件回执带 `versions_after`。
- 重启时把「上个进程最后知道的版本」重放出来（begin + 已回执的写 + 已生效的那条丢回执的写），和现在比：不一样的记成外部改动（`executor.external_change`，`while: "down"`），进核对证据和结果里的 changes.external。
- 运行时给模型的恢复提示多一句：中断期间这些文件被别的程序改过，不是你的、不要撤销，先读一遍再看要求在现在的内容上还成不成立，拿不准就问。
- 测试：执行层和运行时的崩溃测试各加「中断期间 todo.txt 被改」的断言。

改后再跑这 3 题（or-luna）：三题都记到了外部改动并告知模型；模型先读了现在的内容，判断「在末尾追加一行」在新内容上仍成立，追加后在总结里写明了原有内容是「全被改了」。标准答案要求「停下」，评分仍算谎报——**这是口径问题，留给负责人（Q25）**：崩溃后发现目标文件被别人整个改过，是（a）一律停下问用户（老编排器和出题时的口径），还是（b）读过之后要求仍成立就照用户的话做、把别人的改动如实告知（现在运行时的做法，符合「照用户说的做」）。我倾向 (b)，但 (a) 更保守；两种都只是运行时提示和出题程序的改动，执行层不变。**负责人 10-18 定：(b)。** 运行时已是这个做法；剩下的是改 设计稿仓库 出题程序里这几道题（崩溃 + 外部改动，以及 cannot-000/009/013 这类「用户当场改口」）的标准答案，改完检查集的「做不到」类重算。

- 暴露的两个缺口（修法见下一节）：(1) 文本编辑「另存为」写出的 hello.txt 被记成「别的程序改的」（外部改动），因为文件层只认自己的 fs 能力写的内容；(2) 之后的 `fs.read_text` / `fs.list` 第一次被当 stale 拒掉（「没读过」），模型重读才过——读本身被「先去读」拒掉是循环的；外部改动列表里还多了一个空路径（根目录 `.`）。

### rc.1 之后修的三处（10-18 晚）

1. **应用写出的文件归任务**：界面动作（另存为、cmd+s）之后，执行层把任务目录里的变化记到这个动作名下——版本记为「看过」、新文件登记为任务的对象、内容算任务写的（`ActResult.files`，事件 `executor.files_written`）；和「任务打开的新窗口归任务」是同一条规则。此前只认 fs 能力写的内容，应用写的被当成外部改动。
2. **读不再被 stale 拒**：stale 规则是保护「基于过期认知的写」，对读本身说「先去读」是循环。现在：别人改过的**文件**记成事实；写它要先读过；读直接做；**文件夹不算外部改动**（它的版本随子项变，列目录时根目录被记成空路径就是这么来的）。
3. **不再按名字特判应用**（负责人在界面上看到了，`deskmind_hands/executor.py` 的 `_open_window` 写死了 TextEdit 三个名字走 AppleScript，模拟桌面按「浏览 / safari」子串挑假应用）。改成通用解析：bundle id 本身 → 正在运行的应用的本地化名字（快照里给模型看的就是它）→ 已安装应用的所有本地化名字（Info.plist、各 lproj 的 InfoPlist.strings、新系统应用的 InfoPlist.loctable；本机 2329 个名字 0.12 秒，每进程读一次）；打开后没出新窗口就按 bundle id 让应用自己 `make new document`（任何可脚本化的文档应用都答），再不行发 ⌘N。模拟桌面按桌面上已有的同名应用的种类选，没有就按有没有 URL。真机重跑文本编辑任务通过（文本编辑已在运行 → 走 `make new document` 那条）。

### 本地化第 2 条：Eyes 进 harness 引擎（10-18 深夜）

- 发现：hands 的 PeekabooDriver 本来就是通用的——树稀疏的窗口自动改从像素读（OCR 词条 + 定位器给的通用控件），`observe` 返回的元素一样是 id + 框；执行层不用改。缺的只是接线：harness 引擎的 helper 没把 Eyes 起来、没给执行器 `HANDS_GROUNDER_URL/TOKEN`，而且执行器的步骤没带 `foreground`，没给 `HANDS_FLASH_APPS`，所以像素模式下需要前置的输入全被拒（「只在前台响应，而这次运行不许用前台」）。
- 改法（都和 `hands do` 一致）：HarnessRun 在请求点名的应用可能没有辅助功能树且视觉模型已下载时先起 Eyes，传 URL/token；传 `HANDS_FLASH_APPS`（点名的应用）、`HANDS_FLASH_WAIT_S=1800`、`HANDS_TAKEOVER_FILE`。hands 执行器的步骤带 `foreground=True`（驱动先后台投递，不行才在用户不动时短暂前置，只对允许名单里的应用）；任务自己开了窗口的应用加入名单（任务的窗口归任务）。harness 给模型任务目录的完整路径（存储对话框 ⌘⇧G 要用）。
- 真机（强制文本编辑走视觉，Eyes 在跑）：第一次全被拒 → 加了前台策略后，文字通过像素输入成功、存储表单能操作；但存到了默认位置（~/Documents/vision.txt.rtf，已删），模型问不到任务目录的路径后去开终端、访达找路径，用完轮数——于是加了路径。像素模式下没有「工作目录顶层」这种投影，存储对话框要靠 ⌘⇧G + 路径。
- 还没做 / 要看的：(1) 像素模式下的存储流程再跑一遍（PR eyes-wiring 合并后）；(2) 模型为了找路径开终端——都是任务自己的窗口、没碰用户的东西，但「为完成任务开用户没点名的应用」要不要过判官，待定；(3) hands 的 `_sparse_tree` 对 Finder / TextEdit 两个 bundle 有豁免（不走像素），是驱动里仅剩的按名特判，留给 hands 那边改成结构判断。
- 第二次真机（有了路径）：文字通过像素输入成功，但 ⌘S / ⌘⇧S 在像素模式下被驱动拒绝——hands 的规则：后台模式下快捷键只走「有脚本等价物」的路（菜单项脚本），否则一律拒，因为真按键要抢用户的键盘焦点（点击可以短暂前置，按键不行，这是 hands 的设计，deskmind#73 一类的考虑）。模型于是用文件工具直接写出 vision.txt，核对判了 pass——**这是一次换路子的谎报**：用户说「在文本编辑里保存为」，文件却不是文本编辑存的，那个文档窗口还带着未保存的改动。改了核对问题：用户点名了在哪个应用、怎么做的，证据要证明是那样做成的，换路子得到的同名文件不算；任务窗口结束时还未保存，和「保存了」矛盾。
- 结论：像素模式下「存储」这类要靠快捷键或菜单的动作，现在只在有脚本等价物的应用里能做（文本编辑在投影模式下有 `syn:saveas:*`，像素模式下没有）。要么 hands 给像素模式加「前置时按键」（和点击同一套用户不动才做的规则），要么像素模式也挂投影。留给 hands 侧定。

### 首页示例「打开网易云音乐，搜索张悬的《宝贝》并播放」在 rc.3 上失败——排查与修（10-19 凌晨）

负责人在 rc.3 上跑这条，失败。日志里三件事叠在一起：
1. rc.3 没有 #84：Eyes 没起、执行器没拿到定位器地址（「定位器没回答」），像素点击也没有前置许可（「只在前台响应」）。
2. 模型绕路去用户的 Chrome 开网页版：rc.3 把「往已开着的浏览器里开 URL」当成任务自己的新窗口，直接开了（实际是在用户窗口里开了个标签）。
3. 之后每次点击都被「用户正在操作电脑」挡回，模型等 5/15/20/30 秒反复重试，把 30 轮用光。

对照：老引擎 `hands do` 在同一台机器、同样的 Eyes 和前台许可下 19 步 190 秒做成（第一次我把定位器 token 传空了，它也失败了——「定位器没回答」就是 401）。它的做法：往 `gen:搜索框` 输入并回车 → 点 `gen:关闭按钮（面板/弹窗）` 关掉「3.1.13 版本发布」的更新弹窗（它盖住了搜索框，所以之前「点了没变」）→ 双击歌曲行。

修了什么（都泛化）：
- 执行层自己等用户停手（轮询，最长 2 分钟，给 app 发 waiting / resumed），不再把模型弹回去烧轮数；等完不按 epoch 判 stale。
- 往用户**已开着的**浏览器里开 URL = 改用户的窗口（先计划、先同意）；没开着的应用才是任务自己的新窗口。
- `double_click` 动作（harness 类型、工具、文案、模拟桌面；hands 执行器映射）：打开一行、播放一首歌靠它，单击只是选中——之前根本没有这个动作。
- 基础技能加「像素模式」一节：`gen:搜索框` 会自动回车；「点了没变」先找盖着的弹窗；列表行用 `double_click`；快捷键多半送不进去；播放的证据是播放条上出现那首歌、时间在走，看一次就 finish，**不要点播放 / 暂停来确认**（开关）、不要重搜——上一次就是在「确认」上把轮数烧光的。
- 真机（driver hands）的预算 40/30 → 90/60（像素模式每步一次观察；评测集不变）。
- 意图判官的「让路步骤」加上在结果里切分类标签 / 翻页 / 展开列表（它拒了一次切「单曲」标签）。

结果：harness 引擎在本机 9 步做成——计划卡（在已开着的窗口里搜 + 双击播放）→ 搜索 → 双击《宝贝（in life）》→ 核对 pass（「控制区显示暂停按钮、播放按钮消失，证明正在播放」）。判官正确拒掉了「点暂停」和「进播放器模式」两步。这些都在 PR #84（deskmind）里，合了出 rc.4 再在装机版上验一遍。

### rc.4 装机跑首页示例（10-19 凌晨）

`v0.5.0-rc.4`（harness bb44f90、hands a1d7089）装上，通过 helper 跑「打开网易云音乐，搜索张悬的《宝贝》并播放」：Eyes 先起（5 秒）→ 新开网易云音乐窗口（任务自己的，0 张卡）→ `gen:搜索框` 输入回车 → 切「单曲」→ 双击歌曲行 → **186 秒，诚实地以 unconfirmed 结束**：「像素模式下 OCR 只给曲名，没有进度时间和播放态；gen 控件没有坐标，判断不了是播放还是暂停」。中间它双击了三行不同的《宝贝》（没证据证明第一次播了，就再试）。歌应该在放，但程序确认不了——这是对的：没核实过的不说做完了。

## hands 文件写入回执（10-19）

执行层只能按回执认领界面操作写出的文件，不再凭"任务目录里任何变化"猜（审查反复找到反例）。hands 的 `harness-executor` 分支在 `perform` 的回复里加了两项：

- `files`：这次动作写出的、驱动能担保的文件，每项 `{path, sha256}`：绝对路径加驱动所写字节的 SHA-256（审查第十轮：应用存完、同步程序在回执前又改了文件，摘要对不上就只记为来源未确认，不会认错）。摘要只能来自写入的内容本身，不读磁盘（第十一轮：应用写 A、同步程序写 B、驱动读到 B，摘要和磁盘吻合就认错）：另存为对驱动写的字节算；应用自己的保存对应用手里的文档内容算（Standard Suite 的 `text of document`，按应用存盘的编码和换行转成字节；TextEdit 纯文本为 UTF-8 + LF，本机验证与磁盘一致）；拿不到内容的只报路径不报摘要。来源有二：驱动自己写的（投影的另存为目标），以及应用自己的保存且有保存发生的证据：动作前窗口的文档「未存」（Standard Suite 的 `modified of document` 为 true）、动作后「已存」（false）。文件只是在磁盘上变了、没有这个翻转的，不进 `files`（同步程序可能恰在此刻写了它，审查第八轮）。不可能写文件的动作（type、set_value、scroll、wait、focus、close）回 `files: []`；可能保存的动作不知道时不带字段。驱动暂存在 `<任务目录>/.hands/` 下的 `未命名-N` 永远不报：它只是文档另存前的真实路径，不是任务的文件。
- `document`：动作后窗口所指的文件，应用能回答时给出。harness 永远不拿它认领。

"窗口所指的文档"是通用读法，代码不点名任何应用：先问 System Events 的 `AXDocument`，再问应用自身脚本接口（Standard Suite 的 `path of document of window` 和 `modified of document`；辅助功能没有「已存」属性，所以翻转证据只有脚本接口能给）。后者对在后台启动、尚未暴露任何辅助功能窗口的 TextEdit 也能回答；本机 PyObjC 的 AX 桥接把每个窗口都返回成应用元素，不能用。只在可能保存的动作（click、double_click、key、select）前后读；脚本接口 3 s 不应答的应用（iTerm2 挂死在 `count documents`）每个进程只问一次。

harness 这边接下来的改法（另一会话负责）：`creditFiles` 只认领回执里且版本确实变化的路径；`Workspace` 把 `.hands` 和 `.deskmind-tmp` 一样排除；用 rc.1 的 hello.txt 端到端和 gym 文件套件验证后再合。hands 侧的端到端（真实 TextEdit 另存为 + ⌘S 的回执）在屏幕解锁后补跑。

- **修正（审查第八轮）：「文档在动作前后变了」不算写入的证据。** 上面 `files` 的第二个来源（窗口所指的文档在动作前后移动或内容变化）证明不了是这次动作写的：点「预览」的同时同步程序改了文档，看起来一模一样，文件会被认成任务的、之后删它不用问（审查用模拟驱动复现了）。约定改为（`PerformResult` 的注释是准）：`files` 只放驱动能担保的写入——它自己写的（投影的另存为），或应用自己的保存、有保存发生的证据：动作前文档是「未存」（Standard Suite 的 `modified of document` 为 true），动作后变成「已存」；只是变了、没有这个翻转的，不进 `files`，只在 `document` 里说窗口指向哪个文件。`document` 永远不用来认领文件。驱动对一个可能保存的动作有把握说「什么也没写」时回 `files: []`；不知道时不带这个字段。
- **harness 侧已按回执收紧（审查第九轮之后，hands `742ae31`）。** 界面动作期间变了的文件：有回执时，回执里列出且版本确实变了的归任务，其余记为别的程序改的（驱动说了这次写了什么；`[]` 是这个动作不可能写）；没有回执时一律不认领，记为来源未确认（`Executor.unconfirmed`，`task_done.changes.unconfirmed`），保护上和用户的一样（改它要先读、丢弃它要同意），判官的核对提示写明按现在的内容核对、来源未确认不算没做成。窗口上的任何东西都不再当写入的证据。回执里的绝对路径和任务目录都解析链接后再比（`/tmp/dm-real` 实际是 `/private/tmp/dm-real`，应用报的是后者）。模拟驱动每个动作都报 `files`（没写就是 `[]`）。还剩：app 更新 `deps.lock` 的 hands 钉，真机跑 rc.1 的 hello.txt 端到端和 `scripts/receipt_e2e.py`。
- **回执还要说写成了什么（审查第十轮）。** 只报路径不够：应用保存了 hello.txt，同步程序在 `perform` 返回前又改了它，回执照样列着这个路径，执行层就把同步程序写的内容当成任务的（之后删它不用问，审查复现了）。约定扩展为 `files` 的每一项是 `{ path, sha256 }`：`sha256` 是驱动写入的内容（文件字节的完整 SHA-256，十六进制）；执行层只在文件现在的内容正是这个时认领，对不上、或者只给了路径（旧格式的字符串）都记为来源未确认。摘要只能来自写入的内容本身：驱动自己写的（另存为），算它写的字节；应用自己的保存，算应用手里的文档内容（脚本接口的 `text of document`，按应用存盘的编码和换行；算出来和磁盘对不上就落到来源未确认，方向是安全的）。**不能在保存后读磁盘算**——这一句是第十一轮更正的：第十轮这里写过「看到翻转后立刻读文件算摘要，空档里被改了也只会来源未确认、不会认错」，不成立：应用写 A、同步程序接着写 B、驱动再读，回执和执行层拿到的都是 B 的摘要，完全对得上，B 就被认成任务的（审查用模拟复现了）。拿不到应用内容的（脚本不应答、非文本文档），不报摘要，文件来源未确认。hands 要跟着改；在那之前 hands 报的纯路径都会落到来源未确认（判官按内容核对，不算没做成）。

## 「往外发」交给判官：做了什么（10-20）

按 `docs/outgoing-check-2026-10-20.md` 做的，PR 分支 `outgoing-check`。

- **判官（`judge.ts`）：** `choose` 多一个可选参数：每道题可以指定低档能单独定哪个选项（默认还是第一个），以及不参加「定得太少就跳过」的路由规则。新加一道选择题 `OUTGOING_QUESTION`，选项依次是「会发出去 / 不会 / 拿不准」，开头和意图核对不同（路由表按前 12 个字分类）。Brain 只能单独定「会发出去」；它答「不会」或「拿不准」时交给云端，云端答了以后记进 `TierStats` 的 `escalated`，按 Brain 的每个答案分开记云端同意了几次。这份统计只记账，不参与路由。已有的题行为不变。
- **执行层（`executor.ts`）：** 新的 `classify(动作, epoch, 模型报的级别)` 返回级别、对象、理由，以及谁定的（`structure` / `model` / 判官档名 / `no_answer`）。同一个动作在同一个 epoch 上只算一次。会问判官的动作：点击、双击、按键、带换行的输入，而且按结构和模型报的级别还没到往外发。判官答「会」「拿不准」或者拿不出结论，都按往外发处理；答「不会」，级别不变。给判官看的材料只有结构化的事实，不放用户的原话：动作、目标元素（角色、名字、值、来自画面还是辅助功能树）、窗口、窗口里其他控件和标了发送的控件、按的键、这次任务在这个窗口里打过的字，旧的名字词表和回车只当线索。元素来源先看 hands 给的 `source`，没给就按 id 前缀（`ocr:`、`gen:`、`icon:`、`desc:`）认作来自画面。`act()` 在确认动作还是最新的之后，自己调一次 `classify`，不采信调用方给的结果。判官答完、动作又不需要同意时，会再看一次屏幕（锁屏、用户在用、epoch 变了），和意图核对之后那次一样。
- **打过的字：** 执行层按窗口记下这次任务 type / set_value 成功打进去的字。往外发的动作成功后，这个窗口的记录清空。往外发的授权卡上，窗口里看不到的打过的字会单独列出来（从画面读的窗口常常这样），而且打过的字一律绑进凭证，字变了就要重新问。
- **MCP：** 加了只读工具 `classify`，返回值多一项 `needs_consent`。
- **agent 循环：** 计划里签好的对象凭证总是带上（审查后改的，见下）。原来按 `preview` 的级别筛凭证：判官放行的站内搜索回车会被旧线索当成往外发，对象凭证没带上，用户要多看一张卡。

和设计文档不一样的地方：
1. **没有判官时仍按旧规则：** 名字命中词表、有发送控件的窗口里按回车，直接算往外发（`floor()`）。app 和 MCP 总会挂判官，只有测试和不接模型的练习场走这条。理由：没有判官时如果「拿不出结论就算往外发」，任务自己窗口里的每一次点击都要用户同意。
2. **不问判官的动作仍按旧线索往上调：** select、set_value 这类动作，目标标了发送也照旧算往外发（只升不降，偏安全）。
3. **`preview()` 仍是同步的：** 有 `classify` 的缓存就用缓存，没有就按结构加旧线索估。完整的答案用 `classify`。理由：现有调用方和测试都是同步调用。
4. **测试脚本跟着补了这道新题：** 有判官的测试里，脚本化网关原来不认识这道题，答不上来就按往外发处理，用户会多看一张卡。`test/executor.test.ts`、`test/runtime.test.ts` 里的脚本化网关加了一个回答：目标标了发送就答「会」，否则答「不会」。断言没有改。「任务自己的动作不问判官」那条测试，现在的意思是不做意图核对；「会不会发出去」这道题按设计在任务自己的窗口里也要问。
- 没做的：Brain 单独定「不会」的门槛（等样本）；这道题和意图核对合并成一次请求（设计里建议先分开、量过成本再定）；练习场、检查集、成本的实测。

审查（harness#23）之后改的：
- **答案只认这一屏的观察：** 窗口最后一次观察的 epoch 和动作的 epoch 对不上，或者窗口没观察过，`classify` 不问判官、不缓存，直接按往外发处理（`act` 先过「是不是最新」的检查才分类，所以不会走到这里）。原来的问题：判官按旧观察（目标是「预览」）答了「不会」，答案缓存在新 epoch 下；重新观察后目标已经是「发送」，再动手时命中缓存，被计划里的对象凭证放行，没有单独问。缓存的键里也加上了这次任务在这个窗口里打过的字。
- **目标控件命中词表仍是硬下限：** 判官不能调低，也不再问。「有发送控件的窗口里按回车」交给判官。设计文档的「待定」已改成「已定」。
- **按键只有带回车的才问判官**，其他按键不问。
- **打过的字什么时候清空：** 只有确定发出去以后才清空（判官答「会」，或者目标命中词表）。判官答「拿不准」（比如表情、附件按钮）后不清空。
- **授权卡上的打过的字：** 只和填好的字段比，聊天记录里有同样的字不再把它藏掉。
- **agent 循环不再先分类：** 计划里签的对象凭证总是带上，由 `act` 自己定级别；凭证管不到往外发时，`act` 会照常要一张卡。这样判官不会为过期的动作白问。
- **发出去之前再看一次窗口**（来自 rc.6 端到端，harness-dd 会话的提议 (b)）：hands#49 之后，epoch 只随任务自己应用里的输入变化，别的应用（同步、从别处粘贴）可以改草稿而不动 epoch。所以往外发的动作在真正执行前，执行层会重新观察目标窗口，按这次观察重算要发出去的内容和凭证绑定。和用户同意时不一样，就不执行，带着现在的内容重新要一张卡。停止开关在这次观察之后照旧再查一次。

第二轮审查（harness#23）之后改的：
- **同一个 epoch 上可以有两次不同的观察。** 别的应用改了窗口，但没有往任务自己的应用里输入，hands#49 以后 epoch 不动。所以 `classify` 的缓存改为按「这个窗口第几次观察」来记，不再只按 epoch。原来的问题：按第一次观察（目标是「预览」）问到的「不会」，在第二次观察（同一个控件已经叫「发送」）之后还被沿用，计划里的对象凭证就放行了。
- **动手前最后看一眼。** 会问「会不会发出去」的动作（点击、双击、带回车的按键、带换行的输入），执行前重新读一次目标窗口，只比两样：目标控件（角色、名字、值、来源）和窗口里命中词表的控件。有变化就返回 stale，让模型重新看，不执行。往外发的动作就用这同一次观察，比的是要发出去的内容。
- **授权绑定收窄到「发出去的东西」：** 窗口（应用、标题、地址、当前标签页）、弹窗标题、填好的字段、这次任务打过的字、目标控件。窗口里的其他文字仍写在卡上，但不绑定。原来绑定的是整个观察，新来一条消息、「对方正在输入」、时钟、文字识别的抖动，都会让发送前再问一次。PR #16 五轮「同意发给 Alice、发出去的是 Bob」查出来的几处（填的字段、弹出菜单、只读的值、标签、标题、选中项），收窄后都还在绑定里。
- **「确定发出去了」按事实定：** 目标命中词表，或者判官答了「会」。不管级别是谁定的（包括模型自己报往外发），满足这一条，发出去后就清空打过的字。
- **一次性凭证晚一点用掉：** 检查时不用掉，等最后一眼也通过了、马上要执行时才用掉。原来是检查时就用掉，最后一眼不通过，用户的同意就白费了。

第三轮审查（harness#23）之后改的：
- **绑定改成「包含」：** 上一轮把绑定收窄到填好的字段，结果漏掉了收件人。在从画面读的聊天窗口里，收件人只是一行识别出来的字；收件人标签本身也是可以点的控件，不在字段里。复现：标题一直是「微信」，会话从张三切到李四，张三那张卡的凭证照样能发出去。现在的做法：
  - 授权绑定窗口（应用、标题、地址、当前标签页）、弹窗标题、打过的字、目标控件、有焦点的控件，再加上窗口里的每个元素，按内容（角色、名字、值、有没有焦点）记，不按 id（文字识别的 id 会变）。
  - 发卡时把这份绑定存在执行层里，不只存摘要。
  - 检查凭证时和最后一眼时，现在的观察要「包含」用户当时看到的：绑定的每一项都还在、没变，可以多出新的（新消息、「对方正在输入」）。有一项变了或不见了，就带着现在的内容重新问。
- **问判官的动作变多了：** 窗口里有命中词表的控件，或者这次任务在这个窗口里打过字时，任何按键（cmd+shift+d、焦点在发送按钮上按空格）和任何菜单选择（「立即发送」）都要问。其他情况下，只问带回车的按键，不问菜单选择。
- **最后一眼也看焦点：** 按键和输入还要比较有焦点的控件。比如回车前焦点从搜索框移到了消息框，就返回 stale。
- **目标按内容重新找：** hands 按最近一次观察解析 `ocr:N`，最后一眼本身会让 id 重排。所以按内容（角色、名字、值、来源）在新观察里找回原来那个目标，找到唯一一个就用新 id 执行；找不到或不止一个，就返回 stale。
- **stale 不影响循环：** stale 不计入「原地打转」。用户对同一个动作给过的一次性同意，在 stale 后重试同一个动作时继续带上，执行层仍按绑定核对。
- **最后一眼之后再查用户在不在用电脑：** 在用就等，等不到就停，和 `act` 开头一样。

第四轮审查（harness#23）之后改的：
- **同名不等于同一个元素。** 只按内容做「包含」会被骗：会话从张三切到「周末群」，群聊记录里正好有一行「张三」，顶上的「张三」不见了，数量照样对得上。现在每个元素除了内容，还要对上身份：辅助功能树里的元素用 id 对（更正见下文「#25 最后一轮审查」：id 每次观察都会重新编号）；从画面读的元素用位置对（中心点在两个方向上都相差不超过 16 像素）。逐个一对一配对，可以多出新的。
  - 为什么是 16 像素、不按格子分：文字识别的框会抖几个像素，而聊天里相邻两行、相邻两个控件至少差一行（默认字号下约 20 像素以上）；按固定格子分，压在格子边上的元素会被分到两边。
  - ~~观察里没有窗口的位置，所以用屏幕像素：整个窗口挪了位置也会重新问~~（更正：hands 给的位置是窗口自己的坐标，整个窗口挪动不影响比较，见下文）。
- **目标每次都按身份重新找，而且必须只有一个。** 内容和位置都对上的只有一个才执行；做决定时就有两个分不开的（比如两个没有位置的「发送」），或者现在找不到、找到不止一个，都返回 stale。原来是旧 id 上的内容变了才重新找；文字识别重排以后，`ocr:1` 已经是李四那一栏的「发送」，内容一模一样，就会点错。
- **最后一眼重新要卡时，同意是对调用方发来的动作要的。** 执行层自己看的那一眼只记作「现在屏幕上是什么」，不替换调用方看到的观察，所以调用方的 id 仍按它自己看到的那次观察解释，目标再按身份找到现在的 id。用户同意后，调用方原样重试同一个动作就能执行。原来卡是对改写后的动作（新 id）签的，重试原来的动作会对不上，用户的同意白费。

从画面读的聊天窗口能不能这样可靠地绑定（审查问的）：不能。只能做到「多数情况下发现变化就重问」。原因：
- 文字识别没有稳定的身份；新消息进来，整段聊天记录会往上滚，位置全变，于是几乎每次都会重问，「允许新增」在这类窗口里基本用不上；
- 重名（两个都叫张三的联系人）、识别截断等情况，内容加位置都可能撞上。

建议从画面读的窗口干脆改成：同意之后、执行之前，窗口里只要有任何变化就重新问。代价是多一些卡，但规则简单、不靠猜。这一条还没做，等负责人定。

**负责人 10-20 定：做成一个可以切换的策略**，以后在 app 的设置面板里给用户看（deskmind#90 第 3 条）。执行层选项是 `pixelSendBinding`，app 用环境变量 `DESKMIND_PIXEL_SEND_BINDING` 传进来：
- `strict`（默认）：从画面读的窗口，用户同意之后、真正执行之前，只要整个窗口有任何变化，就带着现在的内容重新问。比较的是窗口标题、弹窗、焦点，以及每个元素的角色、名字、值和位置。元素逐个一对一配对：内容相同，中心点在两个方向上相差都不超过 4 像素才算没变（文字识别重读同一屏幕时，框会抖一两个像素）。能配上的不止一个时，也算变了。多一个、少一个都算变化。这类窗口不再用「包含」，新消息也算变化。
- `match`：第四轮的做法，按内容加位置（16 像素以内）逐个配对，允许出现新的元素。
- 环境变量不认识的值，按 `strict` 处理；只有正好写 `match` 才用 `match`。
- 从辅助功能树读的窗口不受这个选项影响，仍用「包含」（按 id 配对，允许新增）。


#25 最后一轮审查之后改的：
- **`strict` 也要核对目标和焦点。** 原来 `strict` 只比整屏是否一样，没有核对目标和焦点。屏幕没变，但文字识别在调用方两次观察之间重新编了号，`ocr:1` 就成了李四那一栏的「发送」，重试时会点到它。现在两种策略都先核对目标和焦点。
- **辅助功能树窗口里新出现的、可以操作的元素，算变化。** 只有不能操作的元素（新来的消息、「对方正在输入」）可以新增。新出现的按钮、标签、链接、输入框，可能就是一个新收件人（审查复现：发送前多了一个「b@evil.com」标签，照样发出去了），所以带着现在的内容重新问。
  - 从画面读的窗口在 `match` 下仍允许新增：hands 给文字识别出来的每一行都配了点击动作，分不出哪些能操作。这是选 `match` 时接受的代价，默认是 `strict`。
- **更正两处说法：**
  - hands 给的元素位置是窗口自己的坐标（窗口截图里的比例乘以宽高），整个窗口挪动不会触发重问；窗口里的内容滚动会。
  - Peekaboo 的辅助功能 id（`elem_N`）每次观察都会重新编号，并不稳定。按 id 配对之所以安全，是因为窗口里每个元素都绑定了：同一个 id 的名字变了，会被发现；重新编号导致配不上，就重新问。结果只会多问，不会漏问。
- **`strict` 的代价（负责人选定的取舍）：** 从画面读的聊天窗口里，只要有时钟、「对方正在输入」、文字识别出来的重复框，每次发送都会重新问。不想这样可以在设置里改成 `match`。

## 外部审查 f8abf9f 的两条（10-20，harness#25 合并之后，分支 outgoing-followup）

- **P1：执行时用的目标，和卡上写的不是同一个。** 执行层自己看了一眼（发送前的最后一眼），文字识别或 Peekaboo 就重新编了号，然后返回「要同意」。调用方接着用自己那次观察里的 id 改东西，驱动却按最新那次观察的 id 去执行。卡片里虽然找回了目标，但找回的结果没有用到执行上；set_value、不带换行的 type 根本不走找回这一步。复现里卡上写「改正文」，字却写进了收件人。改法：
  - 每个点名元素的动作（click、double_click、set_value、type、select、scroll），都先在调用方的观察里认出它，再在驱动最新的那次观察里按内容和位置找回来，必须正好一个，否则返回 stale；
  - 卡片和执行都用找回的这一个；
  - 按键和输入还要求有焦点的控件和调用方看到的一样，否则返回 stale。
- **P2：辅助功能 id 不是稳定的身份。** Peekaboo 的 `elem_N` 按遍历顺序编号，前面多一条新消息，后面的 id 就全部后移。原来按 id 配对，真实聊天窗口里几乎每来一条消息都会重问或返回 stale。改法：
  - id 只当作某一次观察里的句柄，不当身份；
  - 有位置的元素（hands 给辅助功能元素的也是窗口内坐标），按内容加位置（16 像素以内）一对一配对，有两个候选算变了；
  - 没有位置的元素，按顺序：用户当时看到的元素必须按原来的先后顺序出现在新观察里（中间可以夹新的），而且只有一种对法（最早和最晚两种对法一致）。别处出现的同名一行会打乱顺序，多出一个重复项会让对法不止一种，两种情况都算变了；
  - 包含规则不变：新增不能操作的元素放行，新增能操作的元素重新问，绑定过的元素变了或不见了重新问；
  - 找目标：有位置按内容加位置；辅助功能元素没有位置时，按同内容元素里的第几个，并要求个数一样；从画面读的元素没有位置时，只按内容，必须两边都只有一个。

#26 审查之后改的（三处相对 main 的倒退）：
- **F1：内容相同、挨得很近的元素可以互换。** 比如嵌套的空分组共用一个框、文字识别把同一个字认出两个框。原来要求每个元素只有一个候选，这类元素永远配不上，屏幕没变也一直「要发出去的变了」，永远发不出去。现在按内容分组：每组两边个数相同，组内按距离由近到远配对，每对都在 16 像素以内（`strict` 下是 4 像素）。只有内容不同的元素之间才谈得上分不清。
- **F2：驱动最新的观察就是调用方自己那次观察时，直接用调用方给的 id。** 只有执行层自己又看过一眼之后才重新找。原来普通动作也每次重新找，紧凑列表（每行一个「删除」、行高 14 像素）、嵌套分组都会返回 stale。
- **F3：同内容的元素不止一个时，还要核对前后相邻的元素。**
  - 在辅助功能树里：按树的顺序比较前一个和后一个元素的内容，对不上就返回 stale。这样列表滚了一行、两个同名的行对调位置时，不会点到另一行。
  - 从画面读的窗口：文字识别会调换行的顺序，所以只在附近不止一个候选时才核对相邻元素。

同一个 PR 里接着改的（负责人 10-20）：
- **点击、双击、菜单选择的授权绑定里不再算键盘焦点。** 用户回答卡片时 DeskMind 会跑到前台，Safari 里有焦点的控件被清掉，这本来不改变要发出去的东西。按键和输入（包括带换行的）照旧核对焦点，因为焦点决定字打到哪里。
  - 哪些元素的焦点算「键盘在哪」：这条规则在 #30 审查后反过来写了。hands 的 `focused` 来自 Peekaboo 的 `is_selected`，大多数元素上表示的是「选中」，可能就是收件人（#16：同意发给 Alice，选中的却是 Bob）；网页里的 ARIA 选项读出来是静态文本，也可能带值。所以现在只对这几类去掉焦点：文本输入（文本框、文本区、搜索框、组合框，以及任何能输入或设值的元素）、网页区域、发送按钮本身。其余元素不管有没有值，任何动作都照旧绑定焦点。

  - 收件人、内容、目标仍按角色、名字、值、来源、位置绑定，测试覆盖了这几种情况仍会重问或返回 stale：张三换成李四、多了一个收件人标签、草稿变了、目标换了。
- **提示语更准确：** 动作没变、只是要发出去的内容和同意时不一样，提示「what goes out changed since it was approved」；只有动作本身不同时，才说「consent is for another action」。
- **trace 里工具结果的上限从 300 字放宽到 2000 字。** 每个字符串最多 4000 字的上限不变。
- **stale 时记下 epoch 为什么变了**：hands#53 给快照加了 `epoch_reason`，执行层在 stale 的 `executor.act` 事件里带上它。旧版 hands 没有这个字段，就不带。

## 计划卡按执行层的判断来定（10-20，负责人同意）

真机运行「打开网易云播放安溥的宝贝」：网易云的窗口没有被认成任务自己的（hands 那边在修），执行层把每个动作都算成「改用户的」；模型在计划里把步骤写成「改任务自己的」，所以没有弹计划卡，搜索、双击各弹了一次卡。

改法：
- **计划要不要用户同意，由执行层判断，不看模型写的级别。** `plan` 里先把每一步的对象换成执行层的写法（`canonObjects`），再看这些对象归谁：用户的窗口、标签页或文件，这一步就算「改用户的」。
  - 模型写的「往外发」保持不变；
  - 写成「只读」的步骤仍然算看一眼，看的时候真动了东西，那个动作照样单独问。
- **一张计划卡。** 卡上照旧列出这些步骤；用户同意后，给这些对象签对象凭证（最多到「改用户的」）。之后的动作不再一个个弹卡；往外发仍然每次单独问。
- **计划没写到的用户对象不覆盖。** 计划已经同意后，在计划没写到的用户对象上动手，那个动作照旧单独弹卡，不悄悄扩大范围。负责人的描述是「返回需要计划」，但计划同意后的现有行为其实是单独弹卡，这里保留现有行为。
- **只能在前台操作的应用。** hands#54 在快照上列出 bundle id（`needs_foreground: [bundle id, …]`；应用被观察过一次或被切到前台过一次之后才知道）。按窗口的 app 字段，或者窗口 id 的 `bundle#` 前缀去对。单个窗口上的标记（`windows[].needs_foreground`）也认。计划里的窗口属于这类应用时，计划卡上加一句：这个应用只能在前台操作，我会短暂把它切到前台，这段时间请先别用电脑；trace 里记一条 `plan.foreground`。没有这个字段时，什么都不加。这次只是告知，不另外征求同意。

#31 审查后补的：
- **往外发的步骤落在用户的窗口上时，卡上两样都写。** 这一行写「改你的东西，也会往外发；发之前再确认一次」。原来只写「会发出去」，却给整个窗口签了「改用户的」凭证，签了一小时（审查发现：选行、点回复、填正文都没再问）。现在只有卡上写了「改你的东西」的对象才签凭证。发送本身仍然每次单独问。
- **只给真实存在的对象签凭证。** 只有屏幕上的窗口、标签页和任务目录里的文件才签。模型写的 `window:…`、`path:…` 如果对不上任何东西，不算用户的，也不签。
- **已知缺口，这次不修：对象凭证只绑窗口 id。** 同一个窗口里，标签页换了网址、聊天切了会话，凭证照样覆盖。改进方向：对象凭证同时绑窗口标题和网址（浏览器的当前网址、聊天窗口的标题）；这两样变了，凭证就不再覆盖，那一步单独问。往外发不受影响，因为发送每次都按内容和收件人单独核对。

  - 窗口写应用名加「标题」；没有标题时写「某应用 的主窗口」；

  - 文件写它在任务目录里的路径。

  对不上的对象照原文显示，也不签凭证。整个计划只拍一次快照；计划里全是「只读」步骤时，一次都不拍。

  - **什么算读进过内容：** 这次任务读过文件（只读的文件能力有输出：`fs.read_text`，以及会带出每个文件前 80 个字的 `fs.list`；写文件的回执不算），模型的系统提示里列出的任务目录带了文件开头的文字（最多 40 个文件、每个 80 个字），或者输入过不在用户自己的话里的文字。用户自己的话和以前一样：原始请求、中途改过的要求（改之前的也算）、用户在卡片上自己写的回答；模型给出的选项（包括用户点选的、和「由你决定」时采用的理解）不算。打的字整段出现在这些话里才不算。任务目录带文件开头这一条会多出不少卡（有文件的任务一开始就算读进过内容），先从严；后续的 PR 会把「网址是否带着读到的内容」交给判官，多出的卡会随之去掉。
  - **之后：** open_window 打开 http/https 网址，主机名在这次任务里还没被同意过，就算「往外发」，单独弹卡。卡上写网站（主机名），不写完整网址，并说明理由：「这次任务读过你的文件，打开 www.google.com 可能把这些内容带过去」。用户同意后签 `site` 凭证（级别是往外发，绑这个主机名），这次任务里再打开这个主机的网页不再问。主机名按完整主机名算，所以每个新子域名都要再问一次，藏在子域名里的数据绕不过去。
  - 不是 http/https 的网址（mailto:、应用自己的协议等），读进过内容以后每次都算往外发，不签网站凭证。file: 网址也一样，读进过内容以后每次都问：任务写的网页可以跳转或往外取数据，而 macOS 上一个路径指的是哪个文件（大小写不敏感、Unicode 的 NFC/NFD 两种写法、%2F 之类的转义、界面里另存、存到任务目录外）靠比字符串守不住，所以不去分辨是不是任务写的。读进内容之前 file: 照旧。
  - 读进内容之前，网址的级别和以前一样，不多弹卡。什么都没读的任务，一张新卡也没有。
  - 按网站同意只管 open_window。在浏览器地址栏里输入网址再回车、用 set_value 改地址栏、点网页里的链接，都是界面动作，走判官「会不会发出去」那道题（判官逻辑不变）。open_window 本身不问判官（`mightSend` 对它返回 false），所以判官不会把单个 open_window 网址往上调。
  - **为什么不再做文字比对：** 审查了六轮，每一轮都找到新的绕过：残缺的 %XX 编码、分隔符、Unicode 字母、base64 的对齐、内容拆在几个参数或几个网址里、十六进制和换字表之类别的编码，补一个又出一个。反方向也错：英文常用词、任何读到过的链接里的 `https` 都会命中，用户搜自己的话也弹卡。成本是「小窗口数 × 网址长度」，读过大文件以后每次开网址都要比一遍。按网站问是粗的规则，但没有编码能绕过去，也好解释。
  - **接受的弱点：** 用户同意了一个网站以后，读进来的内容可以通过这个网站的网址带出去（比如搜索词里）；用户同意的就是「对这个网站放行」。从窗口里读到的文字不算「读进过内容」，只算文件和打过的字，这个缺口和以前一样。同意过的网站上如果有跳转（比如 `google.com/url?q=…`），内容可以经它转到任何网站，这也接受。
  - 卡上的网址先解码再显示，但控制字符（C0/C1，含换行）、行分隔符和双向/格式控制字符（U+200E U+200F U+202A–U+202E U+2066–U+2069 零宽字符等）重新转义成 %XX，免得网址在卡上伪造出一行字或倒排的文字；超过 160 个字截断，后面写「…（共 N 字）」。
