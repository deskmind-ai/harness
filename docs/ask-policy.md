# 什么时候问用户（设计，10-09）

原则：**问一句的代价比做错的代价小，就问。** 判断分四步，前三步要读懂话和证据，由模型回答；第四步看动作的后果，由代码决定。

## 四步

1. **能自己查到的，不问。** 文件内容、目录里有什么，用只读能力去看。模型在 `missing` 里把这类条目标成 `kind: "observable"`，运行时不发问题，只提示规划先加只读步骤。
2. **查完之后还剩几种说得通的理解？** 模型在 `assumptions` 里，对每个有歧义的地方写出：哪一处（`point`）、选了哪种理解（`reading`）、其他说得通的理解（`alternatives`）、支持它的证据（`evidence`）。只剩一种理解的，不写。
3. **几种理解做出来的结果一样吗？** 结果一样的，不写进 `alternatives`。代码检查不了这一条，由模型负责。
4. **做错了，好不好收拾？** 每个能力自己声明 `reversible`（新建、建文件夹、移动、复制、追加是可撤回的；改写全文、删除不是）。

## 代码的决定

| 情况 | 做法 |
|---|---|
| 某处有歧义，所选理解**没有能区分的证据** | 计划之前就问，问题是「『某处』指的是哪一种？」，选项为几种理解，加「由你决定」和「其他」 |
| 用户说了「随便 / 你看着办」（`user_delegated`） | 计划之后、动手之前，把整个计划一次性给用户确认（不是每一步都问） |
| 有歧义、证据能区分，但计划里有不可撤回的动作 | 同上，一次性确认整个计划，写明用了哪种理解 |
| 有歧义、证据能区分，计划里的动作都可撤回 | 直接做，结果里写明「我是这样理解的」 |
| 没有歧义 | 直接做 |

「能区分的证据」指：目录里的文件名或内容、用户补充的回答。**用户原话本身不算**：有歧义的正是这句话，用它自己证明自己说不通。代码逐条核对证据确实存在。

下面这些与歧义无关，规则不变，每次都单独确认：

- 删除、发送这类有后果的能力；
- 丢弃不是本次任务写出的内容，且用户没有点名要改它。

## 其他提问通道的整理

- **核对动作时信息不足**（intent 判 `insufficient_information`）：核对方要说明缺的东西用户能不能答（`ask_user`）。能答的，给一个简短的问题（`question`）去问；不能答的（缺的是证据），换个绑定再试一次，不去打扰用户。
- **绑定时缺观察**（`missing_observation`）：重新规划一次，先加只读步骤；不再直接失败。
- **图形界面里有后果的按钮**：由界面元素自己的 `consequential` 标记决定，不看按钮文字。
- **所有确认和回答都记成事件**：进程重启后状态一致，不在内存里另记一份。

## 怎么验证

考卷第二版加三个数，一起看：

1. 有歧义的题上，悄悄按错误理解动手的次数：要压到 0。
2. 说得很清楚的题上，多余的提问次数：越少越好。
3. 每道题打断用户的次数：确认和提问都算。

第一个数靠「能区分的证据」那条规则兜底，后两个数用来调「可撤回就先做」这条的松紧。
