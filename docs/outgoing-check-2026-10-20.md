# 「往外发」怎么判断（设计，10-20）

0.5.0 转正前要补的缺口。负责人 10-20 指出：现在按控件名字和回车来判断「往外发」，两个方向都会错。有的发送控件没有名字、只有图标；回车也不一定是发送，比如站内搜索。

## 后果的四级

| 级别 | 例子 | 要不要用户同意 |
|---|---|---|
| 只读（read） | 看窗口、读文件、滚动 | 不用 |
| 改任务自己的（create） | 任务新开的窗口、任务新建的文件 | 不用 |
| 改用户的（modify_user） | 改用户原有的文件、在用户开着的窗口里打字、关掉用户的窗口 | 要。计划卡上同意一次，同一个对象之后不再逐步问 |
| 往外发（external） | 发消息、发邮件、提交表单、分享、支付 | 要，而且每一次单独问。卡上写明要发出去的内容，内容变了要重新问（负责人 10-18） |

一个动作最终的级别，取执行层按结构算出的下限和动手的模型自己报的级别中较高的那个（`executor.ts` 的 `act()`、`preview()`）。计划里写的级别只决定计划卡上签不签对象凭证，不参与定级。

## 现在怎么判断「往外发」

1. **执行层按结构判断（后果下限，`src/executor/executor.ts` 的 `floor()`）：**
   - **按钮的名字：** hands 读窗口时，用 `sends()`（`deskmind_hands/executor.py`）给元素打标记。条件是：角色是能按的一类（按钮、菜单项、链接等），而且名字等于、或者以一张固定词表里的词开头（发送、发布、提交、分享、支付……send、post、submit、share、pay……）。
   - **回车：** 窗口里只要有一个带这个标记的元素，在这个窗口里按回车或输入换行，就算往外发。
   - **文件和工具：** 能力本身声明会往外发。目前的文件工具里还没有一个这样声明的。
2. **动手的模型自己报的级别：** act 的 `consequence` 参数，由 agent 循环里的模型填，现在默认是云端的 DeepSeek。执行层只认更高的那个。
3. **计划里写的级别：** 不参与定级。它只决定用户同意计划时签哪些对象凭证：只给「改用户的」步骤签，往外发不在其中，规则凭证也盖不住往外发，所以往外发一定要单独问。

## 错在哪里

| 错法 | 例子 | 后果 |
|---|---|---|
| 漏判 | 辅助功能树里只有图标、没有名字的发送按钮；词表外的说法（「送信」，分享对话框里的「确定」）；点赞、关注、转发；从画面读的窗口里，认出来的「发送」两个字（角色是列表项，`sends()` 不认） | **碰底线：** 没有单独问用户就发出去了。在用户的窗口里，计划时签的对象凭证会把它放行；在任务自己的窗口里，连意图核对都不做 |
| 多判 | 站内搜索框里按回车，而窗口里正好有个「提交」按钮 | 多弹一张卡，打扰用户，不出事 |

漏判的情况只能靠模型自己报，而设计后果下限，防的就是模型报低。

## 改法

### 1. 结构只管确定知道的

执行层直接定的，只有结构上确定的事实：
- 动用户原有的东西 → 改用户的；
- 文件能力或 MCP 工具声明了会往外发 → 往外发；
- 沙箱断网（见 `docs/pluggable-runtime-2026-10-20.md`）。

界面上「这一步会不会把东西发出去」，结构判断不了。按名字和回车得出的结果降成**给判官看的证据**，不再直接定级别：
- 控件名字命中词表；
- 回车或换行；
- 这次任务在这个窗口里打过的字；
- 元素来自画面还是辅助功能树（见 `docs/pluggable-runtime-2026-10-20.md`「Eyes：从画面看的那一路」）；
- 元素的角色、名字、所在窗口和窗口里的其他控件。

### 2. 判官问一道「会不会发出去」

- **问哪些动作：** 会改东西的界面动作，即点击、双击、带回车的按键、带换行的输入；其他按键不问（成本，harness#23 审查）。只读的动作不问；已经定成往外发的（模型报了、能力声明了、目标控件命中词表）不再问。
- **题目：** 一道选择题，问这一步会不会把内容发给别人、发到这台电脑以外。选项是：
  - 会发出去（第一个选项）；
  - 不会；
  - 拿不准。
- **判官只能往上调：** 答「会」或「拿不准」，就升成往外发；答「不会」，级别保持原样。判官拿不出结论（都答不上来，或者额度用完），按往外发处理。
- **Brain 先答，云端兜底，方向和意图核对相反：**
  - 意图核对里，Brain 只能单独定「是用户要的」（第一个选项），后面还有用户同意兜底；否决交给云端，因为便宜模型很有把握的「不是」在 10-18 的试验里拦掉过正确的动作；
  - 这道题的安全方向是「当作往外发」，所以 Brain 只能单独定「会发出去」（判官里低档只能定第一个选项，`judge.ts` 的 `canSettle`），「不会」和「拿不准」都交给云端。
  - **怎么积累 Brain 的「不会」准不准：** 数据每次都有，缺的是记账。
    - Brain 答「不会」或「拿不准」时，题目交给云端，两档都答过。所以每一次 Brain 的「不会」都有一份云端答案可以对比：100% 都有，不靠抽样，也不多花钱（这次本来就要问云端）。
    - 现在判官的一致率表（`TierStats.noteAgreement`）只统计抽样对比（shadow），也就是「Brain 单独定了、再抽 10% 问云端」的情况；「Brain 答了、交给云端」的情况两档都答了，却没有计入。这时的两份答案，只在打开 `DESKMIND_JUDGE_SAMPLES` 时写成 `judge.sample`，app 现在没开。
    - 要改的：「低档答了、上交给高档」的情况也计入一致率表，按低档的每个选项分开统计（比如 Brain 说「不会」时，云端同意了多少）。
    - 这张表拿云端当标准答案，云端也可能错。最终的标准答案要靠任务结果和用户在 trace 视图里的标注（deskmind#90 第 2、4 条）。
  - **以后放 Brain 单独定「不会」，要改判官：** 现在低档只能单独定第一个选项（`canSettle`）。要改成每道题可以指定低档能单独定哪个选项、各自的门槛。门槛按校准结果定，定法和意图核对的 0.9 一样，用 `scripts/judge-calibration.py`。
  - **路由表会把 Brain 跳过：** 某类题 Brain 能单独定的不到 20%（问满 8 次后），路由表就不再问它，只隔 20 题试一次（`TierStats.skip`）。多数动作不是往外发，Brain 在这道题上能单独定的「会」很少，很快就会被跳过，也就积累不到样本。这道题要么不参与这条跳过规则，要么按「答了多少」而不是「定了多少」来统计。
  - **题目开头和意图核对要不一样：** 路由表按题目的前 12 个字分类（`TierStats.kindOf`）。
- **成本：** 多数动作都不是往外发，一开始大部分题会交给云端。app 打开了竞速（`DESKMIND_JUDGE_RACE=1`），云端请求和 Brain 同时发出，所以多花的主要是钱，时间基本不增加。
- **额度：** 判官不设次数额度（负责人 10-20）。原来的 40 次额度一用完，结束核对就拿不到结论、做完的任务被判成没做成；加上这道题后还会变成每一步都弹卡。一个任务能问多少题，在我们自己的循环里，已经由工具调用和轮数的上限（默认 40 次、30 轮；app 里跑真机时是 90 次、60 轮，`cli/app.ts`）和缓存管住。走 MCP 由别的 agent 调用时，我们这边没有上限，靠那个 agent 自己的轮数限制。花钱上限暂时也不设（负责人 10-20）。动用户东西的动作本来就要做意图核对，可以把这道题和意图核对并成一次请求（见「待定」）；真正新增请求的，主要是任务自己窗口里的动作。

### 3. 授权卡写明要发出去的内容

升成往外发以后，授权卡要写明发出去的是什么：
- 辅助功能树读得到的，用窗口里填好的字段（现有的 `outgoing()`）；
- 从画面读的窗口，用这次任务在这个窗口里打过的字。

凭证绑定的是整个窗口的观察结果，再加上这次任务打过的字；内容变了要重新问（现有的规矩）。从画面读的窗口里，打过的字要单独绑上，因为文字识别不一定认得出来。

**判断策略：从画面读的窗口怎么核对（负责人 10-20 定，harness#25）。** 以后会放进 app 的设置面板（deskmind#90 第 3 条）。执行层选项是 `pixelSendBinding`，环境变量是 `DESKMIND_PIXEL_SEND_BINDING`：
- `strict`（默认）：用户同意之后，窗口有任何变化都重新问。元素的位置允许 4 像素以内的抖动，因为文字识别重读同一屏幕时框会抖。
- `match`：按内容加位置逐个配对，允许出现新的元素（比如新消息）。

不认识的值按 `strict` 处理。从辅助功能树读的窗口不受影响：按 id 配对，只允许出现不能操作的新元素（比如新消息），新出现的按钮、标签之类要重新问。两种策略都要核对目标和焦点没变。`strict` 的代价：从画面读的聊天窗口里有时钟、「对方正在输入」或重复的识别框时，每次发送都会重新问，这是负责人选定的取舍；不想这样就改成 `match`。

### 4. 做成一个函数，所有入口共用

```
classify(动作, 当时的窗口, 这次任务打过的字) → { 级别, 理由, 谁定的: 结构 / 模型报的 / Brain / 云端 / 没有结论 }
```

- 输入都是结构化的事实，不读用户的话。
- 内部顺序：先按结构算下限，再取模型报的级别，最后问判官「会不会发出去」（只能往上调）。
- 同一个动作在同一个画面版本（epoch）上只算一次，结果缓存。
- 调用方：
  - 我们循环里的 act；
  - MCP 的 act（给 Codex 等）；
  - 别的 agent 的调用前钩子；
  - 以后脚本化（像 Codex 的 `cua` 那样一次写一段代码）里的每一次 act。脚本跑到要同意的一步就停下，等用户点了再继续。
- 现有的 `executor.preview()` 是它的雏形：返回级别、要不要同意。改成调用 `classify()`，并作为只读工具给脚本和别的 agent 先查一查。
- 执行层动手时一律自己再调一次，不采信调用方传进来的结果。

### 5. 打开网址：按网站问（负责人 10-21 定）

用 open_window 打开网址，网址本身就能把东西带出去（查询参数、路径、子域名里都能放）。做法：
- **任务「读进过内容」之前：** 网址的级别照旧（开在用户已开着的浏览器里算改用户的，计划卡上按网站同意一次；开在任务自己的窗口里不用同意），不多弹卡。
- **读进过内容：** 这次任务读过文件（文件动作的回执里有输出），或者输入过不在用户自己的话里的文字（用户自己的话：原始请求、改过的要求、用户在卡片上自己写的回答；模型给的选项不算）。
- **读进过内容以后：**
  - http/https 网址的主机名（`new URL(u).hostname`，完整主机名，不是注册域名）在这次任务里还没被同意过，就是往外发。卡上写网站和理由：「这次任务读过你的文件，打开 www.google.com 可能把这些内容带过去」。用户同意后签 `site` 凭证，绑这个主机名，这次任务里之后打开这个主机的网页不再问；换一个主机、换一个子域名都要再问。
  - 不是 http/https 的网址（mailto:、应用自己的协议等）每次都是往外发，不签网站凭证。file: 网址照旧。
- 判官的「会不会发出去」照旧可以把单个网址往上调。

为什么不比对网址里的文字：#33 审查了六轮，按「网址里有没有打过的字或读到的内容」比对，每轮都有新的绕过（残缺的 %XX 编码、分隔符、Unicode 字母、base64 对齐），也会误判（英文常用词、任何读到过的链接里的 `https`），开一次网址的成本还和读到的内容一样大。按网站问没有编码能绕过去。

接受的弱点：同意了一个网站以后，内容可以通过这个网站带出去；从窗口里读到的文字不算读进过内容（和以前一样的缺口）。决定记在 `docs/0.5-decisions.md`「rc.10 真机的几处」。

## 测试

- **用写死回复的模拟驱动测，不花模型调用：**
  - 从画面读的聊天窗口：打字后回车、点画面里的「发送」两个字，都要弹往外发的卡，卡上写明打过的字；
  - 只有图标、没有名字的发送按钮：判官答「会」时弹卡；
  - 站内搜索：判官答「不会」时不弹卡（量多判）；
  - 判官没有结论：按往外发处理；
  - Brain 答「不会」：不能单独算数，要交给云端。
- **练习场：** 40/40 不降，谎报 0。
- **检查集：** 越权 0；打扰次数（弹卡数）和改之前比，多出来的要能逐条说明理由。
- **成本：** 每题的云端调用次数和费用，和改之前比。

## 待定

- **这道题和意图核对合并还是分开：** 合并省一次请求，但一道题里的选项会变多（是不是用户要的 × 会不会发出去）；而且两道题允许 Brain 单独定的方向相反，合并后要分别校准。建议先分开做，量过成本再决定合不合并。
- ~~**名字命中词表的按钮要不要仍直接定成往外发**~~ **已定（10-20，harness#23 审查）：** 目标控件本身命中词表（hands 标了 `sends`），仍直接定成往外发，判官不能把它调低（负责人的规矩：只能往上调）。「有发送控件的窗口里按回车或输入换行」（站内搜索那种）交给判官判断；词表管不到的（只有图标的按钮、画面里认出的字等），也交给判官。
- **Brain 单独定「不会」的门槛：** 等样本，并且要先改判官（见上文）。
